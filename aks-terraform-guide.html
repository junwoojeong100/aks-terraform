1. 먼저 바꿔야 할 사고방식 10가지#

# AWS 에서의 직관 Azure 에서는
1 계정(Account)이 격리·청구·권한 경계 구독(Subscription) 이 청구·쿼터 경계, 리소스 그룹(RG) 이 수명주기·권한·삭제 단위. 모든 리소스는 반드시 RG 안에 있어야 합니다.
2 IAM 사용자/역할/정책 JSON 을 직접 작성 Microsoft Entra ID(디렉터리) + Azure RBAC: "누가(주체) + 무슨 역할 + 어느 범위(scope)" 를 역할 할당 으로 연결. 대부분 내장 역할을 씁니다.
3 서브넷은 AZ 하나에 속함 서브넷은 리전 전체에 걸쳐 있고, 가용 영역(AZ)은 VM·노드 풀·로드밸런서 같은 리소스의 속성입니다.
4 Security Group(상태 저장) + NACL(상태 비저장) NSG 하나가 두 역할을 합니다: 상태 저장, 우선순위(숫자 작을수록 먼저), Allow/Deny 모두 가능. 서브넷 또는 NIC 에 연결.
5 Private subnet + NAT Gateway(라우트 테이블 수정) NAT Gateway 를 서브넷에 직접 연결합니다. 라우트 테이블이 필요 없고, 기본 아웃바운드 IP 에 의존하는 방식은 단계적으로 폐지 중입니다.
6 Gateway/Interface VPC Endpoint Private Endpoint (사설 IP 를 서비스에 할당) + Private DNS Zone 을 직접 구성. 자동 "Private DNS 활성화" 옵션이 없습니다.
7 Role + 신뢰 정책(Trust policy) 리소스형 ID인 Managed Identity(UAMI) 를 만들고, 대상 리소스에 역할 할당을 추가. 키/시크릿 없음.
8 S3 + DynamoDB 로 Terraform state 잠금 Blob Storage 하나로 충분: 잠금은 blob lease 로 자동 처리, 인증은 Entra ID(RBAC).
9 서비스 사용 시 별도 활성화 불필요(대부분) 구독마다 Resource Provider(RP) 등록이 필요합니다(Microsoft.ContainerService 등). azurerm 5.x 는 자동 등록하지 않습니다.
10 EKS 는 내 계정에 노드(EC2)가 그대로 보임 AKS 노드는 별도의 노드 리소스 그룹(MC_... 또는 지정한 이름)에 만들어지고 AKS 가 관리합니다.

2. 조직·계정·리전#

AWS Azure 차이 / 주의
AWS Organizations 루트 Entra 테넌트 + 루트 관리 그룹 테넌트는 디렉터리(사용자·앱)이고, 관리 그룹은 구독을 묶는 계층입니다.
OU 관리 그룹(Management Group) 정책·역할 할당이 하위 구독으로 상속됩니다.

(없음) 리소스 그룹(Resource Group) 수명주기가 같은 리소스를 묶는 컨테이너. 삭제하면 안의 리소스가 모두 삭제됩니다. 태그/잠금/RBAC 범위로도 사용.
SCP Azure Policy + RBAC SCP 는 권한 상한선, Azure Policy 는 리소스 속성을 평가/강제하는 규칙입니다(감사·거부·자동 수정).
Region / AZ Region / Availability Zone koreacentral 은 AZ 3개를 제공합니다. 영역 번호(1,2,3)는 구독마다 물리 AZ 에 매핑이 다를 수 있습니다.
리소스 ARN 리소스 ID /subscriptions/<id>/resourceGroups/<rg>/providers/<RP>/<type>/<name> 형태. Terraform 에서 id 로 서로 참조합니다.
태그 태그 대소문자 구분 없음(키), 리소스 그룹 태그는 자동 상속되지 않습니다(Policy 로 상속 가능). 비용 분석 필터로 사용.

3. 네트워킹#

AWS Azure 차이 / 주의
VPC Virtual Network (VNet) 리전 단위. 주소 공간 여러 개 가능.
Subnet (AZ 고정) Subnet (AZ 비종속) 서브넷에 위임(delegation) 을 걸어 특정 서비스(AKS API 서버 등)가 전용으로 쓰게 할 수 있습니다.
Security Group / NACL NSG, ASG(Application Security Group) NSG 는 서브넷/NIC 에 연결. ASG 는 SG 참조처럼 "논리 그룹" 을 규칙에서 쓰게 해 줍니다.
Internet Gateway (별도 리소스 없음) 공인 IP 가 있으면 인터넷 연결. 아웃바운드는 NAT/LB/방화벽 중 하나를 명시.
NAT Gateway + EIP NAT Gateway + Public IP StandardV2 SKU 는 영역 중복(zone-redundant). 서브넷에 연결.
VPC Endpoint (Interface) Private Endpoint PaaS 별 privatelink.* Private DNS Zone 이 필요합니다.
VPC Endpoint (Gateway: S3/DDB) Service Endpoint 서브넷 → PaaS 공용 엔드포인트를 Azure 백본으로 라우팅. 신규 설계는 Private Endpoint 권장.
Route 53 (Public/Private zone) Azure DNS, Private DNS Zone Private Zone 은 VNet 링크로 해석 범위를 지정.
ALB / NLB Application Gateway(L7), Azure Load Balancer(L4), Front Door(글로벌 L7) AKS 에서는 Gateway API 구현 또는 Application Gateway for Containers 가 ALB Controller 의 대응입니다.
Transit Gateway / VPC Peering VNet Peering, Virtual WAN 허브-스포크: 허브에 Azure Firewall/Bastion/VPN, 스포크에 워크로드.
Network Firewall Azure Firewall 이 실습은 비용을 위해 NAT Gateway 를 쓰고, 방화벽 구성은 부록에서 다룹니다.
VPC Flow Logs VNet Flow Logs NSG flow logs 는 신규 생성이 중단되고 VNet flow logs 로 대체되었습니다.
❗중요

IP 계획이 달라집니다. EKS 의 VPC CNI 는 파드마다 VPC IP 를 소모하지만, AKS 권장 구성인 Azure CNI Overlay 는 노드만 VNet IP 를 쓰고 파드는 별도 CIDR(pod_cidr)을 씁니다. 파드 CIDR 은 VNet/온프레미스와 겹치지만 않으면 됩니다.

4. ID·권한·시크릿#

AWS Azure 차이 / 주의
IAM User/Group Entra ID 사용자/그룹 로그인·MFA·조건부 액세스는 Entra 에서 관리합니다.
IAM Role (사람/서비스가 Assume) Managed Identity(리소스에 부여) + 서비스 주체 System-assigned(리소스 수명과 동일) / User-assigned(UAMI, 독립 리소스). AKS 는 UAMI 를 권장.
IAM Policy (JSON) Role Definition + Role Assignment 내장 역할(Contributor, AcrPull …) 선택 → 범위(scope) 에 할당. 사용자 정의 역할도 JSON.
Permission boundary (없음) / Azure Policy, ABAC 조건 할당 조건(ABAC)으로 일부 구현.
STS AssumeRole 토큰 발급(Entra) 앱은 SDK 의 DefaultAzureCredential 로 자동 획득.
Instance profile Managed Identity (VM/VMSS) 노드(kubelet) ID 가 여기에 해당.
IRSA / EKS Pod Identity Microsoft Entra Workload ID 클러스터 OIDC issuer + Federated credential(issuer+subject) + SA annotation azure.workload.identity/client-id. IRSA 와 구조가 거의 같습니다.

결정 이유
쿠버네티스 리소스는 별도 스택(06) 에서, 클러스터는 이미 존재하는 상태로 클러스터 생성과 같은 스택에서 kubernetes provider 를 쓰면 provider 설정이 apply 시점에 결정되어 계획/삭제가 꼬이기 쉽습니다.

앱 전용 UAMI + Secrets User(읽기) 만 부여 최소 권한. 쓰기는 사람(Secrets Officer)만.
시크릿 값은 ephemeral + write-only(value_wo) Terraform state 에 값이 남지 않습니다 (Terraform 1.11+ write-only 인수, azurerm 5.x 지원). 값을 바꾸려면 value_wo_version 을 올립니다.
네임스페이스에 Pod Security restricted 강제 비루트, 권한 상승 금지, seccomp 등 베이스라인 보안을 네임스페이스 단위로 강제.
RBAC 전파 대기용 time_sleep 역할 할당 직후 데이터 평면 호출이 403 으로 실패하는 흔한 문제를 방지. 시크릿 생성(운영자 권한)과 파드의 시크릿 마운트(앱 권한 + 연합 자격 증명) 모두 이 대기 이후에 진행되도록 depends_on 으로 묶었습니다.

❗중요

왜 Terraform 이 Kubernetes 버전을 "무시"하나요? kubernetes_version = "1.36" 같은 minor alias 로 만든 클러스터는 AKS 가 patch 를 자동 업그레이드하면 실제 버전(예: 1.36.6)이 alias 와 달라져, azurerm 5.9.0 까지는 매 plan 마다 1.36.6 -> 1.36 이라는 불필요한 diff 가 생깁니다(#26946). 이를 억제하는 수정(PR #32625)이 병합되어 v5.10.0(2026-10-15 예정) 에 포함됩니다. 어느 provider 버전에서도 안전하도록 이 실습은 생성 시점에만 버전을 정하고, 이후에는 lifecycle { ignore_changes = [kubernetes_version, default_node_pool[0].orchestrator_version] }(User/Spot 풀은 [orchestrator_version])로 AKS 가 관리하게 합니다. 아래 세 가지 방식 중 팀의 운영 모델에 맞는 것을 고르세요.

방식 누가 버전을 올리나 적합한 경우 이 실습
A. 자동 채널 (stable/rapid) AKS 가 유지보수 창에서 minor 까지 자동 운영 부담 최소화, 개발/소규모 환경 (AKS Automatic 과 같은 모델) automatic_upgrade_channel 값만 바꿔 apply
B. 수동 az aks upgrade 사람이 사전 점검 후 컨트롤 플레인 → 노드 풀 순서로 patch 는 자동, minor 는 통제하고 싶은 운영 클러스터 ✅ 기본 구성 (patch 채널 + ignore_changes)
C. Terraform 이 단일 출처 PR 로 버전 변수를 바꾸고 apply 모든 변경을 코드 리뷰로 남겨야 하는 조직 아래 C-1 / C-2 참고

사전 점검(B, C 공통):

B. 수동 업그레이드 (기본 구성)

버전 변경은 ignore_changes 로 무시되므로 terraform plan 에 diff 가 나오지 않습니다. 다만 나중에 노드 풀을 새로 추가할 때(예: enable_spot_pool = true)는 새 풀이 var.kubernetes_version 으로 만들어지므로, -var kubernetes_version=<현재 클러스터 minor> 로 맞춰 주세요.

C. Terraform 으로 버전까지 관리하기 (전환 방법)

공통: cluster.tf 와 노드 풀(user, spot)의 lifecycle { ignore_changes } 에서 kubernetes_version / orchestrator_version 항목을 제거합니다. 그 다음 둘 중 하나를 고르세요.

  • C-1. 전체 patch 버전을 고정 (모든 provider 버전에서 동작): automatic_upgrade_channel = "none" (노드 OS 교체 node_os_upgrade_channel = "NodeImage" 는 유지), kubernetes_version 은 alias 가 아닌 전체 patch 버전(예: 1.36.4). patch 보안 업데이트도 변수 변경 → PR → apply 로 직접 올립니다.
  • C-2. alias 유지 (azurerm ≥ 5.10 필요): automatic_upgrade_channel = "patch" 를 유지하고 kubernetes_version = "1.36" alias 를 그대로 둡니다. patch 는 AKS 가 올리고(provider 가 alias ≡ 실제 patch 로 취급해 diff 를 억제), alias 를 "1.37" 로 올리면 minor 업그레이드가 plan 에 나타납니다. 5.10.0 은 아직 릴리스 전이라 이 가이드는 5.9.0 으로 검증했습니다. 릴리스 후 terraform init -upgrade 로 올려 plan 에 불필요한 diff 가 없는지 확인한 뒤 사용하세요.

terraform destroy 가 ScopeLocked 리소스 잠금 해제 (Lab 08, Lab 11).

kubelogin 오류 / Unauthorized az login 재실행, kubelogin convert-kubeconfig -l azurecli, Azure RBAC 역할 전파 대기.
terraform plan 이 매번 node_count 변경을 요구 오토스케일러와 충돌. 코드에 node_count 를 쓰지 말고 min_count/max_count 만 사용 (Lab 09).
